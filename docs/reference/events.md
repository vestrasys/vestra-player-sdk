# Events

The player sends an event as one JSON line `{"event": name, "data": …}`, only to plugins that subscribed to that name. Every event reaches a plugin from its first listener. The SDK subscribes for you when a member listens (an `onChange` listener, a stream, a media handle's `ready`). {@link "@vestra-player/sdk"!Player.on | plugin.player.on(event, listener)} listens to a name directly, typed by {@link "@vestra-player/sdk"!EventPayloads | EventPayloads}; {@link "@vestra-player/sdk"!Wire.on | plugin.wire.on} does the same untyped.

- **Payload**: the player's wire shape, not the SDK's view of it (`source.state` says `stamp.generation` where `PlayerState` says `sourceId`). The three source events, `source.opening`, `source.ready` and `source.ended` ({@link "@vestra-player/sdk"!SourceEvent | SourceEvent}, typed by {@link "@vestra-player/sdk"!SourceEventPayloads | SourceEventPayloads}), are the exception: their `state` is the SDK's `PlayerState`. Each is sent once per thing that happened to a source; for one source the order is `opening`, `ready` (none when it could not be opened), `ended`, and a replaced source's `ended` comes before the next one's `opening`. The facts that changed ({@link "@vestra-player/sdk"!FactEvent | FactEvent}, typed by {@link "@vestra-player/sdk"!FactEventPayloads | FactEventPayloads}) are each sent once per change; `audio.tracks.changed`, `subtitles.changed`, `window.changed` and `layout.changed` reach the listener in the SDK's shape.
- **SDK members that listen to it**: from the SDK's request table.
- **Wakes a stopped plugin**: the player starts a plugin on standby for this event, so a listener of it does not keep the plugin running ([Keep a command's state without keeping the plugin running](../guides/command-state.md)); a listener of any other event does.
- **Copy follows only while held**: "yes": the SDK's own copy of that state (`plugin.player.state`, `plugin.window.state`, the layout, the timeline, the appearance) follows the event only while a listener, a watcher (`onChange`) or a stream holds it; otherwise the copy is the newest value the plugin read, and a bound value that reads it shows that. "no": the copy follows from its first use.
