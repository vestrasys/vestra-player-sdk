# Capabilities

A plugin lists what it may do in the manifest's `capabilities` ([Manifest](manifest.md)). A call to a member whose capability is missing fails with code `capability`; nothing else is checked at run time, and capabilities limit only the player API, not the file system or the network (a plugin is a Node.js process). The store shows the capabilities to the user before installing, in the words of the "Shown in the store as" column; the highlighted ones reach outside the plugin's own features.

**Also needs** applies to every member of the row: declare those capabilities as well. A few members or options need one more, documented at the member:

- {@link "@vestra-player/sdk"!Scope.video | video.filter} also needs `events`.
- The changes of {@link "@vestra-player/sdk"!Subtitles | Subtitles} (`select`, `load`, `remove`, `setStyle`) also need `subtitles.read`: they read the current selection first.
- A `processed` snapshot or export ({@link "@vestra-player/sdk"!MediaCapture | MediaCapture}) also needs `playback.read` and `subtitles.read`.
- A file resolver ({@link "@vestra-player/sdk"!Resolvers.add | Resolvers.add} with file types) also needs `producer.av`.
- Without `events`, {@link "@vestra-player/sdk"!Player.state | Player.state} is read at start and after the plugin's own operations, and `onChange` listeners do not fire for changes made elsewhere.

## Without a capability

A member not in the table needs no capability: `plugin.tools`, `plugin.storage`, `plugin.system`, `plugin.app`, `plugin.ui` (images and Markdown), `plugin.i18n`, reading {@link "@vestra-player/sdk"!MainWindow.state | window.state}, {@link "@vestra-player/sdk"!Appearance.theme | appearance.theme}, {@link "@vestra-player/sdk"!Packages.list | packages.list} and {@link "@vestra-player/sdk"!Rendering.state | rendering.state}. The table is `CAPABILITY_INFO`, which tests can import from `@vestra-player/sdk/testing` to check a manifest ({@link "@vestra-player/sdk/testing"!CAPABILITY_INFO | CAPABILITY_INFO}).

## Catching a missing capability

The player refuses a request whose capability the manifest does not declare, at run time. The SDK finds such calls earlier, with one rule: the player's own table of which request needs which capability (copied from the player), and the requests each member above sends. Nothing has to be remembered:

| Where                                     | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The editor                                | An error at the member, "`Player.seek` needs the capability "playback.control", which manifest.json does not declare", with the quick fix **Add 'playback.control' to manifest.json**. It comes from the TypeScript plugin `@vestra-player/sdk/ts-plugin`, listed in the project's `tsconfig.json` (`"plugins": [{ "name": "@vestra-player/sdk/ts-plugin" }]`, as in [Getting started](../tutorials/getting-started.md)). In VS Code, run **TypeScript: Select TypeScript Version** → **Use Workspace Version**: editors load a project's plugins only with the project's own TypeScript. `tsc` ignores language-service plugins. |
| `vestra-plugin check`, `build` and `pack` | `check` reports each use as `file:line:column` with the member, the capability and the request, and fails; `build` and `pack` run `check` first, so a package cannot be made with a missing capability. `check --json` prints the findings as JSON ([Command line](cli.md)).                                                                                                                                                                                                                                                                                                                                                      |

The TypeScript plugin runs inside the editor's TypeScript server, on the editor's own Node.js, and needs that Node.js to be version 22.12 or later (the plugin is an ES module loaded with `require()`; the SDK itself needs 26, but the editor brings its own); current VS Code qualifies. With an older one the server logs that it could not load `@vestra-player/sdk/ts-plugin` and the editor shows no capability errors; `vestra-plugin check` still reports them. The quick fix edits the saved `manifest.json` (editors do not share unsaved JSON buffers with the TypeScript server) and keeps its layout and line endings.

The manifest is the nearest `manifest.json` above the file. Only the plugin's own code is checked: `tests/` (tests choose their capabilities in `startPlugin`), `node_modules/`, `dist/` and `vendor/` are not. A member needs the capabilities its requests need and those capabilities' **Also needs**, so a `video.filter` without `playback.read` is reported too.

The check follows types, not names: `plugin.player.seek`, `const { player } = plugin; player.seek(…)`, a function taking a `Player`, `plugin.clipboard["readText"]` and members of objects other members return (`panel.onChange` on a mounted panel) are all found. Not found: access with a computed name (`player[name]`), values typed `any`, plain JavaScript without types, and options that need more than the member (a `processed` capture, a file resolver). The player's check at run time stays: it is the boundary, since a plugin can bypass the SDK.
