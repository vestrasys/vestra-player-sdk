# Changelog

## 1.7.0

**Who must change: nobody.** The one change a plugin can observe is `Command.set`, which now re-evaluates only its own command instead of running a full update pass: a binding that reads a variable changed together with `cmd.set(…)` outside a handler the SDK runs (a timer, a socket) needs `plugin.update()` after the change, or the variable in `plugin.state` (details under Step 2). Steps 2 and 3 of the SDK refactor (`doc/specs/sdk-refactor.md` §4 in the player repository) and the documentation refactor for the three ways to write a plugin. `apiVersion` stays `vestra/1`, no new capability, no player version needed; every existing golden trace keeps its wire lines and subscriptions, only the update-pass counts drop.

- **New API** (additive, `@since 1.7.0`): `plugin.player.on(event, listener)` for the ten `HostEvent`s, typed `EventPayload<E>`; `plugin.state(initial)`, tracked fields whose writes re-run only their readers; `plugin.wire` (experimental, not semver), the protocol for a plugin's own direct messages: `request`, `on`, `view(v).write`/`writeRows`, `commands.register`; exported wire types: `Wire`, `WireView`, `WireCommands`, `WireCommand`, `WireCommandOptions`, `WireCommandState`, `PropertyWrite`, `RowOp`, `HostEvent`, `EventPayload`, `EventPayloads` and the payload shapes (`WindowFacts`, `PackageInfo`, `WireSource`, `CommandKeys`, `WireTimeline`, `WireMark`, `WireRange`, `WireUpscalingState`, `WireUpscalingReason`, `WireRenderingReason`).
- **Behaviour**: the update passes and the row diff run only for what needs them. A view joins the passes on its first `bind()` (before that `set()` sends whole values), a command only when a state field is a function, and nothing runs while nothing is bound; `Command.set` re-evaluates that command only (above). A property is written either through the view (`set()`/`bind()`) or through `plugin.wire.view(v)`, not both (`invalid`). Raw subscriptions through `plugin.wire.request` to the SDK's own events are refused (use `plugin.wire.on`); other events need `why` or `mirror: true`.
- **Documentation**: a new chapter, "Three ways to write a plugin", with `examples/three-ways`; generated Events and Messages reference pages; style B and C versions of `signal-generator` and `panel-menu`; a "Layers and stability" section in How the player runs and talks to plugins.

**Step 2 of the SDK refactor, "framework optional"** (`doc/specs/sdk-refactor.md` §4 in the player repository): the update passes and the row diff are used only by what needs them, and two new members. On the wire every existing line stays; there are fewer passes. `apiVersion` stays `vestra/1`, no new capability, no player version needed.

- **New: `plugin.player.on(event, listener)`** for each of the ten events (`HostEvent`: `source.state`, `playback.backend`, `window.state`, `packages.changed`, `bindings.changed`, `commands.keys`, `timeline.changed`, `appearance.changed`, `resolvers.fileTypes`, `video.upscaling.changed`). The listener gets a copy of the event's data as the player sent it, typed `EventPayload<E>` (`EventPayloads`); the subscription counts as a listener and carries `why` with the call site (`a listener added at main.ts:12`); no state copy is made for it. Unlike other handlers, no full update pass follows the listener: it pushes its own values (`view.set`), a write to `plugin.state` re-runs that field's readers, `plugin.update()` everything. Disposable and owned by the scope. New exported types `HostEvent`, `EventPayloads`, `EventPayload` (Playback). `vestra-plugin check` checks it by its event name (Step 3, below).
- **New: `plugin.state(initial)`** (`Scope.state`): a tracked object of the same fields. A read inside a `bind` function or a command's state function records the field like a read of `plugin.player.state`; a write that changes a field (`Object.is`) runs one precise update pass that evaluates only those readers. Reads anywhere else are plain reads. One level: a field holding an object is compared by identity. It belongs to the calling scope: once that scope is disposed it is a plain object whose reads and writes schedule nothing. A `bind` function that writes a field it reads would loop; the SDK stops after 100 passes in a row that each changed what they read and reports it once to `onError` (`limit`); the limit counts passes, not loops, so a legitimate chain of bindings deeper than 100 (each writing a field the next one reads) is cut too, and the rest waits for the next full pass. The replacement for manual `plugin.update()` after the plugin's own asynchronous state (`src/plugin/state.ts`).
- **A view takes part in the update passes from its first `bind()`.** Until then `set()` goes straight to the view's writer: every value is sent whole (large lists in parts with `more`, the value limits checked, one write in flight per view), only the properties `set()` named are looked at, and no row-patch base is kept; when the view opens, what differs from its initial properties (a `set()` during the open, an initial list over one request's size) is sent right after; of such a list only the rows the open did not carry go, as inserts on the initial rows, as long as the list still begins with those rows when it is sent (a later `set()` or `bind()`, a write delayed by a back-off, are seen); otherwise, or when the player answers that insert with `stale`, the whole value goes. From the first `bind()` on, `set()` values take the bound way as before (compared, lists patched), so mixing both stays correct. Row-patch planning stays in the writer (`view/writer.ts`), used only for bound views.
- **A command takes part in the update passes only when a state field is a function.** A command of values and `plugin.when` conditions is registered once and never re-evaluated; a function given to `set` binds it from then on.
- **Behaviour change, `Command.set`: it re-evaluates that command only**, sending its state in a microtask (several calls send one `commands.update`), instead of running a full pass over every binding and command of the plugin. A binding that reads a plugin variable changed together with `cmd.set(…)` outside a handler the SDK runs (a timer, a socket) no longer refreshes with it: call `plugin.update()` after the change, or keep the variable in `plugin.state`. Inside a command's `run` or a view callback nothing changes (the pass after the handler still runs). None of the player's built-in plugins or the known third-party plugins relies on it.
- **No pass runs while nothing is bound**: `plugin.update()` and the pass after each handler cost nothing in a plugin without bindings.
- The player's state copy subscribes `source.state` as before: from the start, before the start-up read, whenever the manifest declares `events` (internally it now starts through `PlayerService.start`, which a plugin without `events` reaches on first use, where it subscribes nothing).
- Views and commands keep the order of evaluation of their making (a view bound later is evaluated where it was made), so the order of writes within a pass and of the `why` lines is unchanged.
- **Layer check**: the pending L1 → L2 edges are gone. `plugin.host.run` asks the connection to read the player's state again (`Connection.rereads`), `openStream` and file resolver streams use their own `StreamSource` shape that the player's state copy fills, a package operation's end tells the passes through the connection's `signals`; `validStep` is in `player/rules.ts`. `player.ts` and `state.ts` join the framework list, `player/events.ts` and `player/rules.ts` the primitives, and a rule 6 fails an L0/L1 file that calls the passes by name: `.update()` and `.passes` on any object, `invalidate`, `depends`, `reading`, `part`, `observe`, `reader`, `needsFull` on any object but the connection's `signals`, `runtime.bind`/`runtime.changed` (a textual check: destructured aliases are not seen).
- **Golden traces rewritten** (`test/fixtures/traces/`), each change reviewed: compared with 1.6.21, every `(method, params)` line and every subscription of every existing scenario is unchanged; only the pass counts drop, in each phase the same or fewer. Passes in total: hello 4 → 0, markdown 4 → 0, menus 12 → 8, video 18 → 14, subtitles 11 → 8, playback 20 → 17, playlist 17 → 15, adjust-panel 11 → 8, blur 10 → 8, bookmark 9 → 7, signal-generator 7 → 5, theme-widgets 8 → 7, i18n 4 → 3, panel-menu 4 → 2, info 8 → 6, workshop 5 → 4; binding evaluations fewer in all but playback and signal-generator (video 945 → 626, subtitles 277 → 152, info 16 → 6). Changed fixtures (counts only): `builtins-info`, `-playback`, `-playlist`, `-subtitles`, `-video`, `-workshop`, `examples-adjust-panel`, `-blur`, `-bookmark`, `-hello`, `-i18n`, `-markdown`, `-menus`, `-panel-menu`, `-signal-generator`, `-theme-widgets`; the host scenarios are unchanged. New: `styles-speed-a` and `styles-speed-b`, the plan's speed display (§3) in style A (`bind`, an `enabled` function) and style B (`player.on` + `set`, constant command), from `test/plugins/speed-*`; style B runs no update pass in any phase.
- Tests: `test/framework-optional.test.ts` (a view only `set()` sends whole values and no patch; mixed `set()`/`bind()` stays patch-correct; constant commands send one `commands.register` and no `commands.update` over 20 passes; `Command.set` without a full pass; without `events` nothing subscribes; with `events` a late first read is current; `player.on` payloads equal the wire data, named, no mirror of its own, every event, dispose unsubscribes; `plugin.state` re-runs exactly its readers; `HostEvent` equals the wire's list and each event's capability is the player's) and `test/framework-optional-edges.test.ts` (the review's cases: a `set()` while a never-bound panel mounts or window opens, an initial list over one request on a never-bound panel, `set()` then `bind()`, `Command.set` and other bindings, a first read with `events` but no `playback.read`, `plugin.state` as a plain object, the loop guard, a disposed scope's state, unbound churn, `player.on` refusals and its scope, no full pass per `player.on` event in a bound plugin). The API surface snapshot gains the new members only.

**Step 3 of the SDK refactor, `plugin.wire`** (spec §3.3 and §4 Step 3): one new experimental member, the existing ones unchanged, every existing golden trace unchanged. No new capability, no player version needed.

- **New, experimental: `plugin.wire`** (`Scope.wire`, type `Wire`, Plugin category; `src/plugin/wire-facade.ts`): the protocol and the primitives for a plugin's own direct messages. Every member is `@experimental` and says "the wire protocol is not semver; this member changes with versions": a method or event can change with a player version and a member of `plugin.wire` in any SDK release, without a deprecation period. Prefer the typed members.
  - `request(method, params)`: one request as given, the player's answer typed by the caller; the player checks the capability. Nothing of the SDK in between (no limits, revisions, retries, activation wait). Guarded, with `invalid`: `events.subscribe` and `events.unsubscribe` of one of the ten `HostEvent`s (the player keeps one subscription and one mark per name, and the SDK owns those: listen with `on`, stop by disposing what it returned), and `events.subscribe` of any other event without `why` (a non-empty list of strings) or `mirror: true`, so the player's decision to keep a plugin running (lazy activation) cannot be fooled. Such a subscription to a newer player's event is the plugin's: the SDK does not count it, the plugin unsubscribes it.
  - `on(event, listener)`: a `HostEvent` is subscribed as `player.on` does it, always a listener with its `why` (`a listener added at main.ts:12`), never a mirror; any other name (`commands.execute`, `ui.callback`, a newer player's event subscribed with `request`) is heard without a subscription. The data is a copy, typed `unknown`; no update pass follows.
  - `view(v).write(property, PropertyWrite)` and `.writeRows(property, RowOp[])`: a window's, panel's or settings page's property written below the comparison and the row diff. One write in flight per property (a whole value drops the writes still waiting, which resolve `false`), a `seq` on whole values and lists over one request in parts with a player that takes row patches, row operations numbered on the property's last direct write and split per request; no limits checked (the player's apply). `unavailable` while the view does not show, and for a write the player answers after the view closed or showed its initial properties again; such a write is no base for rows. After a window is shown again a direct property shows its default: `writeRows` without a whole direct write since then is refused with `stale` before anything is sent (write the whole value first). `writeRows` without row patches: `unsupported`. Disposing the view resolves the writes still waiting with `false`.
  - `commands.register({ id, declaration, state?, when?, run? })`: the player's declaration as given, a state of values, `run` on a pick; `WireCommand.update(state, when?)` sends the next revision; without `when` the conditions sent before stay. `commands.add` and `commands.register` share one table of removals in flight, so an id removed by one and added again by the other waits for the removal (no `conflict`). Never evaluated in the update passes. Waited for during activation like `commands.add`, so `TestHost`'s `strictDeclarations` fails `startPlugin` on a refused declaration and the player's runner logs and skips it.
- **One track per property.** A property written with `plugin.wire.view(v)` is the plugin's: `set()` naming it throws `invalid` ("property `rows` is written directly; bind it or write it, not both"), a `bind()` that returns it is reported to `onError` once with `invalid` (its other values still count), and a direct write of a property that was `set()` or bound throws `invalid` ("… is set or bound; …"). The SDK's record of what the player shows stays correct for the properties it compares.
- **New exported types**: `Wire`, `WireView`, `WireCommands`, `WireCommand`, `WireCommandOptions`, `WireCommandState`, and the wire's `PropertyWrite` and `RowOp` (Plugin category, documented to the full standard). `HostEvent`, `EventPayload` as in Step 2. The wire shapes `EventPayloads` names are exported and documented too (Playback): `WindowFacts`, `PackageInfo` with `WireSource`, `CommandKeys`, `WireTimeline` with `WireMark` and `WireRange`, `WireUpscalingState` with `WireUpscalingReason` and `WireRenderingReason`, and the fields of the events whose data has no named type (`playback.backend`, `appearance.changed`, `resolvers.fileTypes`); a `wire.on` listener can type its data with them. The API reference builds again (`npm run docs`).
- **Capability check by name**: `vestra-plugin check` and the editor plugin check `plugin.player.on` and `plugin.wire.on` by their event name (`events`, `bindings.manage`, `commands`, `video.upscaling`; nothing for `packages.changed` or an event that arrives unasked) and `plugin.wire.request` by its method name through the player's table, with the string fields of its parameters (`{ event: "bindings.changed" }`), when the types fix the name to one string (a literal, a constant). A computed name, a union of several, the member taken other than by a direct call (`const { request } = plugin.wire`), or a method the player's table does not know, is listed as **unchecked**: `file:line:column: unchecked: …` on standard output and `unchecked` in `check --json`, a warning in the editor (code 95302); it never fails the check. `plugin.wire.commands.register` needs `commands` (in `CAPABILITY_INFO` and the capability table).
- **Layer check rule 7**: under `src/plugin/` only `wire-facade.ts` (besides `connection.ts`, which defines `Connection.request`, and the test host) sends a request by a method name; `wire-facade.ts` is L1 and reaches a view's writer through a symbol of `view/writer.ts`, loading no view class or binder.
- **Golden traces**: every existing scenario unchanged. New `styles-speed-c`, the plan's speed display in style C (`test/plugins/speed-c`: `wire.on`, `wire.view(bar).write`, `wire.commands.register`): its trace equals style B's line for line, the subscription included (both are a listener with its `why`; only style A's is a mirror), and it runs no update pass.
- Tests: `test/wire-review.test.ts` (the review's probes as regression tests: a cut list bound to another list before its delayed flush, a `stale` insert falling back to the whole value, lists changed while opening, `commands.add`/`register` reusing an id both ways, raw subscriptions to the SDK's events refused, direct writes across a close and reopen (in parts, whole and as a patch: `unavailable`, no base for rows), `writeRows` without a whole write, disposal, one track with camelCase names, direct writes beside a bound list in parts, conditions kept by `update`), `test/wire-facade.test.ts` (raw requests reach the same `TestHost` handlers as the typed clients, refusals keep their code; `events.subscribe` without marks and `events.unsubscribe` refused and nothing sent, with `why` or `mirror` sent as given; `wire.on` subscribes with `why`, never `mirror`, other names without a subscription, dispose stops it; direct writes numbered, patched, sent in parts, replaced while waiting, `unavailable` on a closed window, `unsupported` rows without patches; one track per property both ways and for a binding; `view` of another plugin refused; bare registration, run, update, conflict, dispose; a refused declaration fails `startPlugin`) and `test/capability-check.test.ts` (a literal and a constant method, `events.subscribe` by its `event` field, requires, a union, an unknown or computed method unchecked, `player.on`/`wire.on` by event name, `check` and `check --json` with an unchecked call). ## 1.6.19

**Who must change: nobody.** Step 1 of the SDK refactor, batches B and C (`doc/specs/sdk-refactor.md` §4 in the player repository): `src/plugin/runtime.ts` and `src/plugin/ui.ts` are split by layer; no API, behaviour or wire change, `apiVersion` stays `vestra/1`.

- **`runtime.ts` is split into four modules.** `connection.ts` (L1) owns the transport and its typed client, the event subscriptions with their `why`/`mirror` marks (`on`, `hold`, `raw`), the call site of a listener, the activation state (`starting`, `declaring`, `activated`) and the handshake facts (`app`, `locale`, `features`); `passes.ts` (L2) holds the update passes (`bind`, `reading`, `depends`, `part`, `observe`, `needsFull`, `reader`, `invalidate`, `changed`, the safety pass) and the pass counters; `errors.ts` holds `failure`, `quiet`, `uncertain`, `toError`, `sleep` and `abortError` (from `player.ts`); `latest.ts` holds the `Latest` single-flight queue. `Runtime` stays, as the connection plus the pass methods delegated to its `Passes`, so `runtime.host`, `runtime.on`, `runtime.bind` and the rest are unchanged for every caller, `TestHost` and the player's runner.
- **No module imports the pass scheduler for a helper any more**: the SDK's modules take the helpers from `errors.ts` and `latest.ts`, and `player.ts` and `stream.ts` no longer import each other.

## 1.5.44

**Who must change: nobody.** No changes to the TypeScript API, `apiVersion` stays `vestra/1`, no new capability. How the SDK sends array properties changes, on players that take it (player 0.6.0); with older players it sends whole values as before. The read-only copy of the widget library gains components that need player 0.6.0 (`"minPlayerVersion": "0.6.0"` for a plugin whose Slint uses them; an older player fails to compile such a file).

- **Row patches.** When a bound or set array changes, the SDK sends the rows that changed instead of the whole array: `set`, `insert`, `remove` and `move` operations by index (wire: `ui.setMount`, `ui.set` and `settings.set` with `patch: { base, seq, ops }` instead of `value`; whole writes carry `seq`). Rows are matched by a `key`, `id`, `rowId` or `row-id` field when every row has one, unique, as a string or number (moves are kept to a minimum); otherwise by index, with the unchanged rows at both ends left out. The player writes the rows into its live model in place, without comparing the whole array: selecting one row of a 200-row list costs one row. A player that cannot apply a patch answers `stale` and the SDK sends the whole value at once. Whole values are sent as before when the player does not advertise the feature (`features: ["ui.patch"]` in its start-up data), after a failed write, for rows written into an empty array, for rows holding a Markdown document, and for a value over the limits (refused with `limit`, as before).
  After two `stale` answers in a row for a property, it is sent whole until the view shows its initial properties again. The limit counts see what is sent: an image or document handle is one value, any other object with `toJSON` (a `Date`) counts as what it returns, and a hole in a sparse array is `null`. A released image is refused in any row of the array, also in rows a patch keeps, as in a whole write. ## 1.5.27

**Who must change: nobody.** No API changes, `apiVersion` stays `vestra/1`, no player version needed. Plugins pick the fix up with the player's next SDK upgrade (the player builds the `plugin` object with its own copy); nothing in a plugin changes.

- **Generated streams reach their full frame rate on Windows.** A stream from `openStream` or a file resolver (the NES emulator: one 1/60 s picture per `frame()`) played at 23–26 frames a second on Windows instead of 60. Before, it could only be the whole value of a `[MarkdownBlock]` property. `PropValue` is now `PropData | ImageRef`, where the new **`PropData`** is JSON whose values may also be `MarkdownRef`s, at any depth. A released document is refused with `invalid` wherever it is in the value. An `ImageRef` stays a whole value only: nested in an array or object it is `invalid` (a type error in TypeScript, and refused by the SDK and the player). Older players refuse a nested document like any value they cannot convert.
- **Limits:** a document still holds at most 256 KB of text, 4000 blocks and 64 images; all of a value's text, its documents' text included, counts toward the value's 1 MiB; each document is one of its 4096 values.
- **`MarkdownBlocks`** (new in `@vestra/markdown.slint`): the blocks of a document without scrolling, as tall as their content, for your own layout or a `ListView` row. `in [MarkdownBlock] blocks`, `in bool code-copy` (default `false`), callbacks `link-clicked(string)` and `copy-code(string)`. `MarkdownView` is now a `ScrollView` around it and gains the same `code-copy` and `copy-code`; it looks as before.
- **Code copy, opt in.** With `code-copy: true`, code blocks get a 复制 button that reports `copy-code(code)` with the block's text; the plugin copies it (`plugin.clipboard.writeText`). Off by default: views that do not set it look and behave as before.
- **Cheaper updates** (player): writing a value again with unchanged documents does not parse them again (a new reference for the same text included), and a value with documents is updated in place where its shape allows: changed rows, rows added or removed at the end, and only the changed blocks of a changed document. Streaming a reply into the last row of a 200-message list therefore keeps the list, its scroll position and the other rows. Nothing to change in plugins.
- `TestHost` keeps nested documents in the view's properties as they were sent; `host.markdown(value)` reads one back from a field (`host.markdown(rows[0].body)`).

## 1.5.3

**File resolvers: local files as generated streams** (player 0.4.1). Additive; `apiVersion` stays `vestra/1`. Plugins that register one set `"minPlayerVersion": "0.4.1"`: an older player refuses the declaration (`invalid`).

- **`resolvers.add({ id, extensions, resolve })`** (`FileResolverOptions`). When anyone opens a local file of those extensions with `player.open` (the Open dialog, the playlist, next / previous, the recent list), the player asks this plugin for a stream instead of playing the file. `resolve(path, signal)` returns a `ResolvedStream`: `{ kind: "stream", width, height, frame, started? }`, with the frame contract of `openStream`. Needs `source.resolve` and `producer.av`. `ResolverOptions` is now the union of `WebResolverOptions` (the existing form) and `FileResolverOptions`.
  - The open keeps its arbitration: its `ifCurrent` and operation (the opener's `open` / `media.ready()` settle as usual), and `paused` reaches the stream's start. `state.source` stays the path, `state.kind` is `"stream"`.
  - Cancellation: `signal` aborts when the open is replaced or closed (`player.close()` included), times out (30 s) or the resolver is disposed. Cancelled after `resolve` returned but before the stream ran, the SDK releases the stream and never calls `started`.
  - `started(stream)` is called synchronously right after activation, before any `onStop`; the `Stream` is the same as `openStream`'s and belongs to the resolver's plugin.
  - Extensions: 1–16 entries of 1–16 lower-case letters or digits, not `"folder"`; only absolute local paths match (any case), URLs never do.
- **One extension, and one scheme + host pair, has one resolver.** Another plugin's makes `Resolver.ready` reject with `conflict` (reason `resolver-taken` on the wire), and that no longer fails activation, for web resolvers too (as for panels and the sequence since 1.5.2); the player shows a warning (`PluginInfo.warnings`: `code` `"resolver-taken"`, `owner`, the new `target`). The plugin's own second claim still fails activation.
- **Resolver failures are sent as the error's message** (`error.message`, was `String(error)`, e.g. `"Error: …"`), and the player shows them word for word (it prefixed `resolver failed: `). This changes the failure text of web resolvers too.
- **Docs**: `PlayerState.source` documents the naming of generated streams: `producer://<n>` (opaque) for `openStream`, the path for a file resolver's; tell streams apart by `kind`.
- **`TestHost`** simulates file resolutions: opening a matching path (`player.open`, `openElsewhere`) sends `source.resolveRequest` and keeps the open pending; the answer selects the stream (or fails the open); any later source change cancels it (`source.resolveCancel`). `resolutions` lists the pending ones, `otherResolvers` simulates other plugins' registrations (conflicts). `startPlugin` does not fail activation for such a conflict. Web resolutions are still driven by the test (emit `source.resolveRequest`).
- Internals: `openStream` is split into prepare / activate / abandon steps shared with file resolvers; the wire client (`sourceResolvers.register`) takes a `{ id, extensions }` declaration and a handler answer with the prepared producer.

## 1.5.2

**Sidebar tabs** (the player after 0.4.0). Additive; `apiVersion` stays `vestra/1`, and plugins written for 1.5.1 need no change. The new members work against older players too (see each one).

- **Several sidebar panels.** A plugin mounting in the sidebar while another plugin's panel is there no longer fails: its `ready` resolves and the panel is a second tab. The player draws a 31px tab strip (the playlist's) above the current tab while there are two or more; with one panel nothing changes. Shown, hidden and floating apply to the whole sidebar. Tabs are labelled with the mount's `title` (else the plugin's name); built-in plugins' tabs come first, the playlist's is the first.
- **`Panel.state`** (`PanelState`: `active`, `preferred`, `effective`, `reason`, `detached`) and **`Panel.onChange`**: the panel's own state. A panel in a background tab has `active: false`, `effective: false` and `reason: "otherTab"`. Older players report the position's state with `active: true`.
- **`Panel.show()`** makes the panel's tab current and shows the sidebar; **`Panel.toggle()`** hides the sidebar when the panel's tab is shown, otherwise shows it (a background tab comes forward). Use them for a "Show my panel" command: `checked: () => !!list.state?.preferred && !!list.state?.active`. Older players: `setVisible(true)` / `toggle()` of the position.
- **`PanelSlot.panels`** (`SlotPanel[]`: `plugin`, `title`, `active`) lists a position's tabs, `null` from older players; `PanelSlot.onChange` also runs when only the tabs change. **`PanelSlot.activate(plugin)`** switches the current tab (older players ignore it). `SlotState` is unchanged.
- **The `tabbed` property.** If a sidebar panel's bridge global declares `in property <bool> tabbed`, the player sets it to `true` while it draws its tab strip, so a panel with a tab strip of its own (the playlist) hides it. Drop coordinates (`Panel.onDrop`) start below the strip.
- **`Panel.showMenu`** in a background tab rejects with `unavailable`.
- **Taken positions** (player 0.4.x after 0.4.0, documented now): the bottom bar and the backdrop take one panel; another plugin's mount there rejects `ready` with `conflict` (「底栏已被 vestra.playback 使用」), as does a ninth sidebar tab. This refusal, and `conflict` from `player.provideSequence` while another plugin provides next/previous, do not fail activation in the player: the plugin runs without its panel or sequence. Players 0.4.0 and older answered a taken bottom bar or sidebar with `ui-prepare` and failed the activation.
- **`PluginInfo.warnings`** (`PluginWarning`: `code` `"slot-occupied"` or `"sequence-taken"`, `slot`, `owner`): what a running plugin was refused because another plugin holds it. Empty from older players.
- **`TestHost`** models both: `host.mountOther(slot, plugin, { title })` and `host.unmountOther(plugin)` simulate another plugin's panel (a sidebar tab, or a taken bottom bar or backdrop: the plugin's mount then rejects with `conflict`), `host.selectTab(plugin)` the user clicking a tab; `host.layout.sidebar.panels` / `.owner` are the tabs and the current one, `layout.set` takes `active`. `startPlugin` does not fail on a taken position, like the player.
- Examples: panel-menu no longer asks you not to load it with the playlist; it is a second tab there. Its list ends in a stretching filler: without it the rows' fixed heights capped the player's main window at its minimum height.

## 1.5.1

Fix; no API or type changes.

- **`storage.json` saves no longer collide.** Every save wrote through the same temporary file (`<name>.json.tmp-<pid>`), and only the writes of one store were queued. Two stores on the same file (the same name opened twice, in one scope or two) could therefore rename each other's temporary file away mid-save, and the save failed with `ENOENT` (on `chmod` or `rename`); on Windows two renames onto the file at once also fail with `EPERM`. Seen intermittently on Windows.
  - Writes to one file are now queued together, whichever store makes them, and land in the order they were made.
  - Each write has a temporary file of its own, made owner-only (`0600`) through its file handle before it gets the store's name, and removed again if the write fails.
  - On Windows, replacing the file is retried for up to 2 s while another program (a virus scanner, the search indexer) briefly holds it open.
